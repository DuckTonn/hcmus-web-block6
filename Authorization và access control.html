B. Mô hình

IDOR và BOLA

Server trả object theo ID, không kiểm quyền trên object

IDOR: Insecure Direct Object Reference

Ứng dụng nhận tham chiếu trực tiếp tới object (ID trong URL, query hoặc body) và trả object đó mà không kiểm quyền. Thuật ngữ có từ OWASP Top 10 năm 2013; hiện lỗi này thuộc nhóm Broken Access Control (A01:2021).

BOLA: Broken Object Level Authorization

Tên của lỗi này trong OWASP API Security Top 10 (API1:2023). Endpoint nhận object ID cần kiểm quyền ở mức object; thiếu bước kiểm đó là BOLA.

Ba điều kiện gây lỗi

  • 1Object ID do client gửi lên
  • 2Token hợp lệ nên request qua authentication
  • 3Server không kiểm quan hệ giữa người gọi và object

Chỉ đổi ID, token giữ nguyên

GET /tasks/A1   Bearer <token Alice>
200 task của project Alpha

GET /tasks/B1   Bearer <token Alice>
200 task của project Beta

Mã minh họa

// Lỗi: chỉ kiểm token
app.get('/tasks/:id', auth, (req, res) => {
  res.json(db.tasks.get(req.params.id))
})

// Sửa: kiểm quyền trên object
app.get('/tasks/:id', auth, (req, res) => {
  const task = db.tasks.get(req.params.id)
  if (!task || !canRead(req.user, task)) return res.sendStatus(403)
  res.json(task)
})
ID khó đoán (UUID) chỉ làm việc dò khó hơn, không thay kiểm quyền: ID vẫn có thể lộ qua log, email hoặc response khác.

B. Mô hình

Bốn mô hình access control

Cùng một câu hỏi: Bob sửa được task không?

ACL

quyền ghi trên từng resource
task A1:  alice edit, bob edit
task A2:  alice edit
cho phép Bob sửa A1: ACL của A1 có dòng bob edit
từ chối Bob sửa A2: ACL của A2 không có Bob
Đánh đổi: thêm task mới thì phải thêm dòng cho từng người.

RBAC

quyền gắn với role
Bob là Member của project Alpha
Member: read, edit      Viewer: read
cho phép Bob sửa A1: Member có quyền edit
cho phép Bob sửa A2: role không phân biệt task
Đánh đổi: không biểu diễn được điều kiện riêng của từng task.

ABAC

quyền theo thuộc tính
sửa được nếu task.assignee == user
          và task.status == Open
cho phép A1: giao cho Bob, đang Open
từ chối A2 chưa giao; A1 đã Closed
Đánh đổi: assignee và status phải do server giữ, không lấy từ request.

ReBAC

quyền theo quan hệ
bob --member--> Alpha     A1 --thuộc--> Alpha
sửa được nếu user là member của project chứa task
cho phép Bob sửa A1: Bob và A1 cùng nối tới Alpha
từ chối Bob sửa B1: Bob không có quan hệ với Beta
Đánh đổi: phải truy vấn quan hệ; cache và thu hồi phức tạp hơn.
Các mô hình dùng cùng nhau được. Ví dụ ở V3: RBAC (Member có quyền sửa), ReBAC (Bob thuộc project chứa task), ABAC (task giao cho Bob, còn Open).

VẤN ĐỀ 2: Danh sách chậm
Kiểm quyền từng task bằng một truy vấn riêng. Danh sách 1000 task (giả định) tốn 1001 truy vấn.

mỗi task: canRead -> hỏi DB    // 1000 truy vấn
GIẢI PHÁP: đưa điều kiện vào truy vấn danh sách

SELECT t.* FROM tasks t
JOIN project_members m
  ON m.project_id = t.project_id
WHERE m.user_id = :user

1. Token có scope tasks:read có đủ để Alice đọc task B1 không? Vì sao?
Không đủ. Scope giới hạn quyền của token, không cho biết Alice có quan hệ với B1. Server vẫn phải kiểm Alice có thuộc project chứa B1 hay không.
2. Khi dùng role Member, hệ thống còn cần kiểm tra dữ liệu nào trước khi cho sửa task?
Project của task (Member của project nào), assignee, status của task, và tenant. Role chỉ trả lời Member làm được loại thao tác nào.
3. Vì sao ẩn nút Delete trên giao diện không ngăn được request trực tiếp?
Giao diện chạy ở phía client nên chỉ ảnh hưởng người dùng bấm nút. Request gửi bằng curl hay script không đi qua giao diện, nên server phải tự kiểm quyền.
4. Với hàng triệu tài liệu chia sẻ qua nhiều nhóm, policy nên được tổ chức như thế nào để tránh khác biệt giữa các API?
Một điểm quyết định dùng chung cho các entry point; quan hệ chia sẻ lưu như dữ liệu thay vì viết điều kiện riêng trong từng API; tách check và list; cache có TTL và quy trình thu hồi; một bộ test dùng chung.
